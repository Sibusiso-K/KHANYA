# REEFPRINT / KHANYA — first S2 v2 training result

**Status:** first controlled baseline completed on 29 September 2026. This is a research and hackathon result, not a validated plant model.

## What was run

The [private Kaggle kernel](https://www.kaggle.com/code/lethabomh14/reefprint-s2-v2-private-baseline-training) trained the repository's DeepLabV3–ResNet50 patch segmenter on the publisher's [LumenStone S2 v2](https://imaging.cs.msu.ru/en/research/geology/lumenstone) dataset. The S2 archive was fetched directly from the publisher inside Kaggle, matched the locally verified SHA-256, passed ZIP CRC validation, and contained all 37 training and 12 held-out test image/mask pairs.

## Held-out test report

The frozen checkpoint was evaluated once on all 12 test sections at native resolution using 512 px sliding windows. These are pooled pixel metrics over these images, not locality-level estimates; the publisher package does not provide a locality/specimen grouping file.

**Pooled macro mIoU:** 0.4543 across five classes. **Pixel accuracy:** 0.7716. Pixel accuracy must not be presented alone because background dominates the image area. Three required sulphides have non-zero pooled IoU on this dataset, but chalcopyrite and pentlandite remain weak and magnetite fails completely.

## What this result supports

- The pipeline runs end to end on Kaggle GPU compute, uses a frozen test split, produces a checkpoint and accuracy report, and can classify the three required sulphides at least on some held-out pixels.
- The local project runtime (`torch 2.13.0+cpu`, `torchvision 0.28.0+cpu`) strictly loaded every checkpoint key. A 512×512 synthetic forward pass produced finite logits with shape `(1, 5, 512, 512)`. This checks file/architecture compatibility; it is not an image-quality validation.
- The checkpoint and metrics are copied into the application branch's gitignored `checkpoints/lumenstone_s2_patches/` folder. We do not commit 168 MB of derived weights or source data to Git.

## What it does not support

This is one small-dataset baseline. The 12 images are not 12 independent localities. No confidence intervals, cross-mine generalisation, sensor/lighting robustness, processability prediction, XRF fusion, 3D geospatial integration, or live plant-control test has been demonstrated. Do not say the model is plant-ready or that it improves recovery. The Kaggle run is private, and this result is not a commercial data/model rights determination.

## Next work without reusing the test set

1. Preserve this checkpoint, metrics and run bundle as the baseline. Do not change thresholds or training settings based on these test metrics.
2. Diagnose the validation/train behaviour and class counts using only the training and six validation images. For chalcopyrite and pentlandite, inspect false-positive locations and boundaries; for magnetite, check label codes/remapping and sampled patch presence before changing losses or sampling. Keep every attempt as a new run ID.
3. Add labelled sections from a distinct specimen/locality as the next external evaluation set. Six validation images from the same publisher split are not enough to establish reliable generalisation.
4. Show outputs honestly in the demo: phase overlay, per-phase scores, uncertainty/low-quality abstention and a clearly labelled simulated process response. Do not connect this model to live plant controls.
5. Before application acceptance, run at least one real training-image inference through the dashboard, verify overlays and timings, and make sure every display labels this as research output.

The raw archive, output bundle and extracted checkpoint remain in ignored local staging. The Kaggle kernel logs and the checkpoint's test report are the evidence source for the values above.
